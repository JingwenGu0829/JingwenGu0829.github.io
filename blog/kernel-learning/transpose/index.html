Matrix Transpose

A transpose performs almost no arithmetic. That makes it a clean experiment in what actually matters to a GPU memory system: not only where the bytes live, but which addresses a warp requests together.

Problem

Given a contiguous row-major rows × cols float32 matrix, write its contiguous cols × rows transpose: output[col, row] = input[row, col].

Constraints: 1 ≤ rows, cols ≤ 8192. The performance case is 7000 × 6000: 42 million values, or 168 MB read plus 168 MB written.

Source: LeetGPU — Matrix Transpose ↗. Challenge revision: AlphaGPU/leetgpu-challenges ↗.

v00

Direct scalar mapping

Start with the most literal correct kernel: one thread moves one value.

Knowledge point: logical coordinates are not memory transactions

A row-major layout turns a two-dimensional coordinate into a one-dimensional word offset. The transpose changes the coordinate, then the output layout maps that new coordinate back to storage:

input_offset = row × cols + col output_offset = col × rows + row

CuTe's Tensor makes the same separation explicit: it carries an iterator and a layout, and input[row, col] asks that layout for an address. A rank-two tensor[linear] should not be treated as a raw-pointer offset, so this first version keeps the two coordinates explicit.

v00_naive_scalar.py complete baseline 
import cutlass.cute as cute


BLOCK_SIZE = 256


@cute.kernel
def transpose_kernel(
    input: cute.Tensor,
    output: cute.Tensor,
    rows: cute.Int32,
    cols: cute.Int32,
):
    thread_idx, _, _ = cute.arch.thread_idx()
    block_idx, _, _ = cute.arch.block_idx()

    linear_idx = block_idx * BLOCK_SIZE + thread_idx
    element_count = rows * cols
    if linear_idx < element_count:
        row = linear_idx // cols
        col = linear_idx - row * cols
        output[col, row] = input[row, col]


@cute.jit
def solve(
    input: cute.Tensor,
    output: cute.Tensor,
    rows: cute.Int32,
    cols: cute.Int32,
):
    """LeetGPU entry point: launch enough threads for all matrix elements."""
    element_count = rows * cols
    grid_size = cute.ceil_div(element_count, BLOCK_SIZE)
    transpose_kernel(input, output, rows, cols).launch(
        grid=[grid_size, 1, 1],
        block=[BLOCK_SIZE, 1, 1],
    )

Profile: both arrays are in HBM, so why are load and store different?

Coalescing happens when the memory unit combines the 32 lane addresses of one warp instruction into cache-line sectors. It happens before those requests reach HBM. Here adjacent lanes load adjacent input words, only 4 bytes apart, so a warp's 32 float32 loads occupy one 128-byte span. The stores are different: adjacent lanes increase col, so their output addresses are rows × 4 = 28,000 bytes apart.

Next hypothesis Change transaction shape, not the math

Read rows coalesced, temporarily stage a square tile, then read that tile by columns so the output can also be written as contiguous rows.

v01

A shared-memory tiled transpose

Use shared memory as a coordinate-changing scratchpad between two coalesced global accesses.

Knowledge point: a 32 × 8 block can move a 32 × 32 tile

CUDA linearizes thread coordinates with threadIdx.x varying fastest. Because blockDim.x = 32, every fixed ty is exactly one warp and lane_id = tx. This launch mapping and a CuTe tensor layout use the same coordinate-to-linear idea, but they describe different things: CUDA maps threads to lanes; CuTe maps tensor coordinates to addresses.

Thread block 32 × 8 = 256 threads

Eight warps; each warp is one row of 32 adjacent tx values.

Per-thread work j = 0, 8, 16, 24

Each thread moves four elements. range_constexpr exposes these four rounds at compile time.

Data tile 256 × 4 = 1,024 values

The same coverage as 32 × 32 threads, without making every CTA a maximum-size 1,024-thread block.

The load phase writes ordinary rows into shared memory; no data has moved to a transposed position yet. After the barrier, exchanging the two shared-memory indices turns one column read into one contiguous output row.

Why the barrier is mandatory.

A value loaded by warp 0 may later be consumed by warp 7. sync_threads() is both a CTA rendezvous and the shared-memory visibility boundary between these phases. Its cost is not a fixed mysterious tax: fast warps wait only when slower warps have not finished. Removing it would create a correctness race, not a valid performance tradeoff.

Code: v01

This is the first strategy rewrite, so a diff against v00 hides more than it reveals. The complete tiled kernel makes the two phases and their shared coordinate system easier to read together.

v01_smem_tiled.py complete tiled kernel 
import cutlass
import cutlass.cute as cute


TILE_DIM = 32
BLOCK_ROWS = 8


@cute.kernel
def transpose_kernel(
    input: cute.Tensor,
    output: cute.Tensor,
    rows: cute.Int32,
    cols: cute.Int32,
):
    tx, ty, _ = cute.arch.thread_idx()
    bx, by, _ = cute.arch.block_idx()

    smem = cutlass.utils.SmemAllocator()
    tile_layout = cute.make_layout(
        (TILE_DIM, TILE_DIM),
        stride=(TILE_DIM, 1),
    )
    tile = smem.allocate_tensor(cutlass.Float32, tile_layout)

    input_col = bx * TILE_DIM + tx
    for j in cutlass.range_constexpr(0, TILE_DIM, BLOCK_ROWS):
        input_row = by * TILE_DIM + ty + j
        if input_row < rows and input_col < cols:
            tile[ty + j, tx] = input[input_row, input_col]

    cute.arch.sync_threads()

    output_col = by * TILE_DIM + tx
    for j in cutlass.range_constexpr(0, TILE_DIM, BLOCK_ROWS):
        output_row = bx * TILE_DIM + ty + j
        if output_row < cols and output_col < rows:
            output[output_row, output_col] = tile[tx, ty + j]


@cute.jit
def solve(
    input: cute.Tensor,
    output: cute.Tensor,
    rows: cute.Int32,
    cols: cute.Int32,
):
    transpose_kernel(input, output, rows, cols).launch(
        grid=[
            cute.ceil_div(cols, TILE_DIM),
            cute.ceil_div(rows, TILE_DIM),
            1,
        ],
        block=[TILE_DIM, BLOCK_ROWS, 1],
    )

allocate_tensor describes one 4 KiB allocation per CTA. Every thread executes code that can index the tensor, but the compiler does not allocate 256 copies; all threads in that block see the same CTA-local shared-memory region. Multiple CTAs can reside on one SM, each with a disjoint allocation carved from that SM's shared-memory capacity.

In (32, 32):(32, 1), the first tuple is the logical coordinate domain and the second is each coordinate's contribution to the linear word offset: offset(row, col) = row × 32 + col. make_layout defines that mapping; allocation binds the mapping to storage.

Profile: global traffic is fixed; shared traffic is not

v01 drops from 692.03 to 197.15 µs. NCU reports zero excessive global sectors, which confirms that the load and store sides are now both coalesced. But it also reports 43.316 M actual shared-memory wavefronts versus 2.630 M ideal: 40.686 M are excessive.

What improved Global sectors: ideal

The scratchpad successfully turns the transposed output into contiguous warp stores.

What moved The bottleneck is now inside the SM

The column read tile[tx, fixed_col] sends every lane to a different word in the same bank.

v02

Remove bank conflicts with padding

Change one number in the physical shared layout: the row stride becomes 33 instead of 32.

Knowledge point: banks serve a warp instruction

An SM's shared memory is physically split into 32 banks. For float32 words, the useful mental model is bank = word_offset mod 32. A bank can serve one distinct word per wavefront. If multiple lanes request different words in the same bank, the warp instruction is decomposed into additional wavefronts. Lanes reading the exact same word are a broadcast and are not this conflict pattern.

Banks belong to the SM, while shared allocations belong to CTAs resident on that SM. Those facts are orthogonal: the bank hardware is shared, but the conflict calculation is about the 32 addresses in one warp instruction—not threads from unrelated warps or CTAs.

Code: v01 → v02

The global coordinates, four load rounds, barrier, transposed shared read, and four store rounds are all unchanged. This is the useful part of reading the implementation as a diff: the 2.02× speedup below is attributable to one physical-layout change.

Profile: one padding column halves the time

Shared memory grows from 4,096 to 4,224 bytes per CTA—only 128 bytes. NCU now measures exactly 2.630 M actual and ideal shared wavefronts, with zero excessive shared wavefronts and still zero excessive global sectors. Runtime falls to 97.78 µs, 2.02× faster than v01 and 7.08× faster than v00.

How to read “wavefronts” in NCU.

A high raw wavefront count alone does not prove bank conflicts; a large kernel naturally issues many shared-memory requests. Compare actual with ideal, or inspect the excessive count. In v01, 94% of shared wavefronts are excessive. In v02, actual equals ideal.

v03

Replace padding with a CuTe XOR swizzle

Keep a compact 32 × 32 allocation and permute its bank-select bits instead.

Knowledge point: a CuTe layout can be affine, or composed with a swizzle

The ordinary row-major layout first maps (row, col) to offset = row × 32 + col. For a 32 × 32 tile, the low five offset bits are the column/bank field and the next five bits are the row field. cute.make_swizzle(5, 0, 5) XORs those five row bits into the five bank bits:

source bits row [5, 10)
XOR
destination bits column [0, 5)
→ physical_col = col XOR row

XOR with a fixed row is a permutation, so every row access still touches 32 distinct banks. XOR with a fixed column is also a permutation as row varies, so the transposed column read becomes conflict-free too. The logical coordinates used by the kernel do not change; only their mapping to the underlying shared words changes.

Profile: conflict-free does not automatically mean faster

v03 is correct, compact at 4,096 bytes per CTA, and NCU again reports zero excessive shared wavefronts and zero excessive global sectors. It measures 98.94 µs—statistically close to, but about 1.2% slower than, padding in this run.

Detailed replay explains the tradeoff: the swizzled version executes 56.26 M instructions versus 45.08 M for padding, about 24.8% more, because scalar address generation must apply the XOR mapping. The 128-byte shared-memory saving does not improve occupancy for this kernel, so v02's simple affine address calculation wins on this exact shape and hardware.

For scale, a same-shape contiguous device copy measured 88.16 µs (3,811.25 GB/s effective) in a quick reference run. That is not a formal hardware roof, but v02 reaches about 90% of this practical copy reference while also changing coordinates.

Measured winner v02 · padding

Minimal address work; the extra 128 B has no occupancy cost here.

More general tool v03 · swizzle

Compact and composable; valuable when padding affects footprint, alignment, or a later copy atom.

Takeaways

GPU programming model

  • HBM is a location; coalescing describes the shape of one warp's addresses before requests reach it.
  • A shared tile can exchange coordinates between a coalesced input phase and a coalesced output phase.
  • Bank conflicts are per warp instruction. Use actual versus ideal wavefronts—not the raw total—to diagnose them.
  • A 32 × 8 block keeps one warp across a row while four compile-time rounds cover a 32 × 32 tile.
  • Synchronization is required when one warp consumes another warp's shared-memory writes.

CuTe DSL mental model

  • A layout maps logical coordinates to a one-dimensional address; it does not allocate storage itself.
  • allocate_tensor binds a typed layout to one CTA-local shared allocation visible to every thread in the block.
  • range_constexpr expresses a static loop that the compiler can unroll.
  • make_composed_layout(swizzle, 0, base) applies the affine layout first, then remaps its address bits.
  • Swizzle is not universally superior to padding: resource savings matter only if they change the limiting resource.

This is a good stopping point for transpose. The next machinery—multistage asynchronous copies and TMA—becomes much more instructive in GEMM or attention, where data movement can overlap substantial compute instead of another memory operation.
